# 02 — Forward mode and dual numbers

> Dual numbers as the quotient ring `R[ε]/(ε²)`, its universal property
> as the *carrier of first-order Taylor data*, the chain rule on duals,
> forward-mode AD as a Jacobian-vector product (JVP), the connection
> to the tangent bundle, and the multi-direction extension that gives
> `JetK`. Anchors: `Jet1`, `JetK`, `ops::compute_gradient_fwd_k`.

## Overview

Forward-mode AD augments every scalar `v` with one extra component
`\dot v`, the *tangent*. The tangent records "the rate of change of `v`
with respect to a chosen input direction." Every elementary operation
propagates both components together: the primal value as usual, and the
tangent via the operation's local derivative and the chain rule.

In `xad-rs` the single-direction case is [`Jet1<T>`](https://docs.rs/xad-rs/latest/xad_rs/forward/jet1/struct.Jet1.html);
the multi-direction case — propagate against a full tangent vector
instead of a single tangent scalar — is
[`JetK<T, K>`](https://docs.rs/xad-rs/latest/xad_rs/forward/jetk/struct.JetK.html),
which fixes the direction count at compile time and stores the tangents
in a `[T; K]`. Used on its own, either is tape-free and allocation-free,
and both are `Real` modes: a generic body evaluates `K` input directions
in one `JetK` pass, and
[`compute_gradient_fwd_k`](https://docs.rs/xad-rs/latest/xad_rs/ops/derivative/fn.compute_gradient_fwd_k.html)
drives `⌈n/K⌉` such passes for a full gradient with no tape. `JetK` has a
second role as the *storage scalar* of a reverse-mode tape, which is what
turns the seed-matrix idea into an exact Hessian engine (chapter 04).

## Theory

### Dual numbers as a ring

A **dual number** is a formal pair `(a, b)` written `a + b ε`, where
`ε` is an indeterminate with the rule `ε² = 0` (and `ε ≠ 0`).
Equivalently, the dual numbers form the quotient ring

```math
\mathbb{D} \;=\; \mathbb{R}[\varepsilon]\,/\,(\varepsilon^2),
```

the polynomial ring `R[ε]` modulo the ideal generated by `ε²`. Every
element of `D` has a unique representative `a + b ε` with `a, b ∈ R`,
and arithmetic is forced by linearity, distributivity, and the
nilpotent rule `ε² = 0`.

```math
(a + b\,\varepsilon) + (c + d\,\varepsilon) \;=\; (a + c) + (b + d)\,\varepsilon.
```

In words: dual numbers add componentwise — the real parts add, and the
ε-parts add.

```math
(a + b\,\varepsilon)\,(c + d\,\varepsilon) \;=\; ac + (ad + bc)\,\varepsilon
\quad\text{since}\quad bd\,\varepsilon^2 = 0.
```

In words: the real part of a product is the product of the real parts,
and the ε-part of a product is `a*d + b*c` — exactly the right-hand side
of the product rule from calculus.

```math
\frac{a + b\,\varepsilon}{c + d\,\varepsilon} \;=\; \frac{a}{c} + \frac{bc - ad}{c^2}\,\varepsilon
\quad (c \ne 0).
```

In words: the real part of a quotient is `a/c`, and the ε-part is
`(b*c - a*d)/c^2` — exactly the quotient rule. (To derive it,
multiply numerator and denominator by the conjugate `c - d ε`; the
denominator becomes `c² + 0`, and the numerator becomes
`ac + (bc − ad) ε`.)

`D` is a commutative ring with unit `1 = 1 + 0 ε` and zero
`0 = 0 + 0 ε`. It is *not* a field — the element `ε` is a zero divisor
(`ε · ε = 0` with `ε ≠ 0`). For AD this is a feature: the nilpotency
`ε² = 0` is exactly what truncates the Taylor series at first order.

### The universal property

The ring `D = R[ε]/(ε²)` has a clean universal characterisation that
explains why dual numbers are *the* algebraic object for first-order
derivatives, not merely *an* implementation choice:

> **Universal property.** A ring homomorphism `R[X] → S` for a
> commutative `R`-algebra `S` is completely determined by where it
> sends `X`. Restricting to homomorphisms that send `X` to a *nilpotent*
> element (`X² ↦ 0`) factors through `R[ε]/(ε²)`. So `D` is initial
> among commutative `R`-algebras equipped with a distinguished
> nilpotent square-zero element.

The practical reading: any computation in `D` is uniquely determined by
the primal value `a` and the "infinitesimal kick" `b`. Running a
program of elementary operations in `D` instead of `R` is the *most
general* first-order linearisation of the program. There is nothing to
choose, no convention to fix; the algebra forces the answer to be the
derivative.

For any smooth elementary `f`, *define*

```math
f(a + b\,\varepsilon) \;=\; f(a) + f'(a)\,b\,\varepsilon.
```

In words: applying a smooth function `f` to a dual number takes the
real part `a` to `f(a)`, and lifts the ε-part to `f'(a)` times the
incoming `b`. This is exactly the first-order Taylor expansion of `f`
truncated at order ε² = 0:

```math
f(a + b\,\varepsilon)
\;=\; f(a) + f'(a)(b\,\varepsilon) + \tfrac{1}{2}f''(a)(b\,\varepsilon)^2 + \cdots
\;=\; f(a) + f'(a)\,b\,\varepsilon \pmod{\varepsilon^2}.
```

The higher-order terms vanish because `ε^k = 0` for all `k ≥ 2`.

### The chain rule, as a one-line proof in `D`

The compatibility of the dual-number definition with composition is the
chain rule, and it falls out of the algebra in three lines.

> **Lemma (chain rule in `D`).** For smooth `f, g : R → R` and
> `a, b ∈ R`,
> `f(g(a + b ε)) = (f ∘ g)(a) + (f ∘ g)'(a) · b · ε`.

*Proof.* Apply `g`: `g(a + bε) = g(a) + g'(a) b ε`. Now apply `f` to
this dual number, treating its real part as `g(a)` and its ε-part as
`g'(a) b`: `f(g(a) + g'(a) b ε) = f(g(a)) + f'(g(a)) · g'(a) b · ε`.
The ε-coefficient is `f'(g(a)) g'(a) b = (f ∘ g)'(a) · b`. ∎

In words: evaluating `f ∘ g` on a dual number gives back, in the
ε-coefficient, exactly the derivative of `f ∘ g` times the seed `b`.
The chain rule is *literally* the second step of dual-number
evaluation.

This is the algebraic reason forward-mode AD is correct: a Wengert list
of elementary operations evaluated in `D` instead of `R` returns a dual
number whose primal part is the program's value and whose ε-part is the
program's derivative — by induction on the list length, using the
elementary chain-rule lemma above at each step.

### How `Jet1<T>` implements this

`Jet1<T>` stores exactly two `T`s: the primal `value` and the tangent
`derivative` (call them `a` and `b`). The operator impls implement the
rules above. From [`src/forward/jet1.rs`](https://github.com/sercanatalik/xad-rs/blob/main/src/forward/jet1.rs):

```text
(a + b ε) * (c + d ε) = (ac, ad + bc)            — Mul impl
(a + b ε) / (c + d ε) = (a/c, (bc - ad)/c^2)     — Div impl
f(a + b ε)            = (f(a), f'(a) * b)        — math::fwd::f impls
```

Seed with `derivative = 1` on the input you want to differentiate
against; propagate; read `derivative()` off the output. This is the
entire forward-mode-in-one-direction machinery.

### Forward mode as a Jacobian-vector product

Generalising from scalar to vector: if `F: R^n → R^m` is a function,
the directional derivative of `F` at `x` in direction `v ∈ R^n` is the
Jacobian-vector product (JVP)

```math
F'(x; v) \;=\; J(x)\,v \;\in\; \mathbb{R}^m.
```

In words: the directional derivative is the matrix-vector product of
the Jacobian `J(x)` with the chosen direction `v`. Each coordinate is
the rate of change of the corresponding output component as you walk
infinitesimally from `x` along `v`.

Forward AD computes exactly `J(x) v` in one forward pass. The seeding
recipe is:

- Replace each input `x_i` with `(x_i, v_i)` (primal value, tangent =
  the `i`-th component of `v`).
- Run the program. Every intermediate is now a dual pair.
- The output `y` is a vector of dual pairs `(F_j(x), (J v)_j)`. The
  ε-parts form `J v`.

To recover a single column of `J` — say `∂F/∂x_k` — seed with `v = e_k`,
the `k`-th unit vector. To recover the full `J`, you would need `n`
passes, one per column. Reverse mode (chapter 03) recovers `n` columns'
worth of information in one pass but the dual operation: vector-Jacobian
products, i.e. `u^T J`, one row at a time.

### Multivariate dual numbers and the seed-matrix view

For multi-direction propagation, the cleanest algebraic setting is the
ring of *multivariate* dual numbers:

```math
\mathbb{D}_n \;=\; \mathbb{R}[\varepsilon_1, \ldots, \varepsilon_n]\,/\,(\varepsilon_i \varepsilon_j : i, j \in \{1, \ldots, n\}).
```

In words: `D_n` is the polynomial ring in `n` formal indeterminates
modulo *every* pairwise product. Equivalently, an element of `D_n` is
`a + b_1 ε_1 + ⋯ + b_n ε_n` with `a, b_1, …, b_n ∈ R`, and any product
of two ε's is zero. The product rule generalises:

```math
\Bigl(a + \sum_i b_i \varepsilon_i\Bigr)\Bigl(c + \sum_j d_j \varepsilon_j\Bigr)
\;=\; ac + \sum_i (a\,d_i + b_i\,c)\,\varepsilon_i.
```

For smooth `f`,

```math
f\Bigl(a + \sum_i b_i \varepsilon_i\Bigr)
\;=\; f(a) + f'(a)\,\sum_i b_i \varepsilon_i \pmod{\varepsilon_i \varepsilon_j}.
```

Evaluating a program of elementary operations in `D_n` with input `x_i`
seeded as `x_i + ε_i` returns an output whose ε_k-coefficient is exactly
`∂F/∂x_k`. The whole gradient drops out in *one* forward pass.

`JetK<T, K>` is the literal implementation, with the number of
directions fixed at compile time: each value stores a primal `T` plus a
`[T; K]` of ε-coefficients — one tangent *lane* per seeded direction.
Every binary op runs one elementwise loop over the lane array (which
auto-vectorises), and an elementary `f` scales every lane by
`f'(value)`.

```math
\nabla f(x) \;=\; J^{\,T}(x) \cdot 1 \;=\; \text{output tangents after seeding } I_n.
```

In words: for a scalar-valued `f`, the Jacobian is a row vector and the
gradient is its transpose. Seeding with the identity matrix (each input
`x_i` seeded with `e_i`) and reading the output's tangent vector yields
exactly that gradient.

In `xad-rs` this construction earns its keep one level up rather than as
a standalone gradient mode: for a scalar output and `n ≫ 4`, reverse mode
(chapter 03) recovers the whole gradient more cheaply than any number of
forward lanes. What the seed-matrix view *is* indispensable for is
**second** order — using `JetK<f64, K>` as the storage scalar of a
reverse-mode tape propagates `K` Hessian columns per sweep. That is
[`compute_hessian_k`], and it is developed in
[chapter 04](04-second-order-and-k-jets.md).

[`compute_hessian_k`]: https://docs.rs/xad-rs/latest/xad_rs/ops/hessian/fn.compute_hessian_k.html

### A geometric interlude: the tangent bundle

For readers who like the geometric view, here is the differential-
geometry interpretation of forward mode.

A smooth function `F : R^n → R^m` induces a map on **tangent bundles**

```math
TF : T \mathbb{R}^n \;\to\; T \mathbb{R}^m, \qquad
TF(x, v) \;=\; (F(x),\; J(x)\,v).
```

A tangent bundle element `(x, v)` packages a base point `x` with a
tangent vector `v` at that point. The map `TF` lifts `F` to act on
tangent vectors via the Jacobian.

A dual number `a + b ε` is exactly an element of `TR ≅ R × R` — the
base is `a`, the tangent is `b`. Multivariate dual numbers `D_n`
correspond to `TR^n ≅ R^n × R^n`: the base is `(a_1, …, a_n)`, the
tangent is `(b_1, …, b_n)`. *Evaluating a program in `D_n`* is
precisely *applying `TF`*, the tangent lift of the program's
underlying smooth function.

This is not merely an analogy. It is a *theorem* of synthetic
differential geometry (Kock 1981, Lawvere 1967): the smooth maps `R^n
→ R^m` are in bijection with the `R`-algebra homomorphisms `D_n → D_m`
that preserve the projection to base points. The "AD interpretation" of
forward mode and the "differential geometry interpretation" are the
same construction.

### A scalar `Real` impl is single-direction

The `Real` trait is implemented for `Jet1<f64>` (one direction) but
**not** for the dense second-order `Jet2Vec`. The reason is the trait's
`From<f64>` requirement: building a `Jet2Vec` from an `f64` requires
knowing the input-space dimension, which the trait API cannot pass
through. `JetK<T, K>` has no such problem — its direction count is a
const generic, so `JetK::constant(x)` is well defined — which is why a
kernel written once as `fn f<R: Real>(..) -> R` composes with the K-wide
Hessian engine but not with `Jet2Vec`.

## Cost model

Let `P` be the flop count of the primal pass and `n` be the number of
input directions you seed against.

| Type | Time | Memory (per live value) | Output |
|---|---|---|---|
| `Jet1<T>` | ~2P (primal + one tangent op per elementary) | 1 extra `T` | One scalar tangent (one column of `J`) |
| `JetK<T, K>`, `K` directions | ~(1 + K)P, sublinear in `K` in practice | `[T; K]` inline | `K` tangents at once |

For a scalar-output function (`m = 1`), `K = n` directions collapse to
one forward pass for the full gradient. For a vector-output function,
both give you exactly the directional information you seeded — you still
need one pass per *direction*, not per *output component*.

The `~(1 + K)P` figure is pessimistic: the lane loop is a fixed-size
array operation that auto-vectorises, so measured per-pass cost grows
noticeably slower than `K`.

Compare with reverse mode (chapter 03): there, time scales with `m`
(number of outputs you take adjoints of), not `n`. Crossover is at
`n ~ m`; for `n ≫ m` reverse wins.

The dual-of-tangents structure makes forward mode amenable to SIMD: the
lane loop in `JetK` is a fixed-length `[T; K]` traversal, which is
exactly why `xad-rs` stores its tangents in an inline array rather than
a heap buffer or a tagged union.

### A note on transcendentals

The cost of `Jet1` and `JetK` is *not* always exactly `2P` and
`(1+K)P`. Transcendentals (`exp`, `sin`, `ln`, …) have local derivatives
that often share work with the primal: `(sin x)' = cos x` requires `cos
x` which is cheap given `sin x` was just computed; `(exp x)' = exp x`
shares its derivative *with the primal itself*. Modern hardware also
computes `sincos` jointly. So the "constant 2–4" estimate folds in
these primal-sharing optimisations; the worst case is closer to
`(1 + a + b·K)P` with `a` the per-call AD overhead and `b` the
per-lane overhead, both small.

## Anchored API

- [`xad_rs::Jet1<T>`](https://docs.rs/xad-rs/latest/xad_rs/forward/jet1/struct.Jet1.html) — single-direction, single-order.
  - `Jet1::new(value, derivative)`, `Jet1::constant(value)`,
    `Jet1::value()`, `Jet1::derivative()`.
- [`xad_rs::JetK<T, K>`](https://docs.rs/xad-rs/latest/xad_rs/forward/jetk/struct.JetK.html) — `K`-direction, single-order.
  - `JetK::new(value, tangents)`, `JetK::constant(value)`, and the
    public `value` / `tangents` fields.
  - Its purpose is to be the tape storage scalar of
    [`compute_hessian_k`](https://docs.rs/xad-rs/latest/xad_rs/ops/hessian/fn.compute_hessian_k.html);
    see chapter 04.
- AD-aware transcendentals: [`xad_rs::math::fwd`](https://docs.rs/xad-rs/latest/xad_rs/math/fwd/index.html) (`sin`, `exp`, `pow`, `norm_cdf`, ...).

## Worked example

A three-input gradient by seeding the identity matrix into `JetK`, with
the analytic answer in comments. `Float` is in scope because `JetK`
propagates its transcendentals through that trait.

```rust
use num_traits::Float;
use xad_rs::JetK;

fn main() {
    // f(x, y, z) = x^2 * y + sin(z), at (x, y, z) = (3, 4, 0.5).
    // df/dx = 2*x*y = 24
    // df/dy = x^2   = 9
    // df/dz = cos(z) ~ 0.8775825618903728
    const N: usize = 3;
    let x = JetK::<f64, N>::new(3.0, [1.0, 0.0, 0.0]);
    let y = JetK::<f64, N>::new(4.0, [0.0, 1.0, 0.0]);
    let z = JetK::<f64, N>::new(0.5, [0.0, 0.0, 1.0]);

    let f = x * x * y + z.sin();

    assert!((f.value - (9.0_f64 * 4.0 + 0.5_f64.sin())).abs() < 1e-12);
    assert!((f.tangents[0] - 24.0).abs() < 1e-12);
    assert!((f.tangents[1] -  9.0).abs() < 1e-12);
    assert!((f.tangents[2] - 0.5_f64.cos()).abs() < 1e-12);
}
```

The whole gradient drops out of one forward pass — no tape, no reverse
sweep, no analytic differentiation by hand. Seeding lane `i` of input
`x_i` is the multi-direction generalisation of "seed `derivative = 1`"
from the `Jet1` case, and corresponds to evaluating the program in `D_n`
with seed matrix `I_n`.

For a scalar output and more than a handful of inputs this is *not* how
you should compute a gradient — reverse mode (chapter 03) is
asymptotically cheaper. The construction earns its keep when the same
lanes ride on top of a tape and yield Hessian columns; see chapter 04.

## Common pitfalls

- **Seeding the wrong lane.** Reusing the same lane index for two
  different inputs collapses them into one variable; the derivative you
  read back is `∂f/∂(x_i + x_j)`, not what you wanted.
- **Reaching for `K` lanes when `Jet1` suffices.** If you only need one
  directional derivative, `Jet1` is cheaper.
- **Reaching for forward mode when the tape wins.** For a scalar output
  and many inputs (the typical pricer setup), reverse mode is
  asymptotically cheaper — `O(1)` time in `n` instead of `O(n)`. Use
  `Tape` + `AReal` for `n ≫ 4`. Chapter 03 develops this, and the
  crate's own `swap_pricer` example measures it at `n = 30`.
- **Mutating the primal after construction.** `JetK::value` is a public
  field; do not overwrite it unless you understand exactly what the
  tangents now represent.
